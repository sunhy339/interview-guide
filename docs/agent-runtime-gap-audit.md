# Agent Runtime 对照审计与补缺清单

## 1. 审计结论

当前产品已经不是“只有一个聊天接口”的 Agent：它具备模型优先的意图路由、按能力裁剪工具、面试报告/简历/文件/RAG/Skill 的显式上下文、有限 Agent Loop、动作草稿与人工确认、会话持久化、重启基础恢复、长期记忆、用量统计、审计和提示注入防护。

它目前更准确的定位是：**受控的单 Agent 业务运行时**，而不是自由探索式的多 Agent 系统。这个定位适合面试、简历、知识库和日程场景，也更容易保证“输入简单、结果可控、业务数据不被模型直接修改”。

对照主流 Agent Runtime 后，最大的差距不在“再增加几个按钮”，而在以下三件事：

1. 运行中断时，当前模型轮次和结构化待处理项还不能完整恢复。
2. 工具结果已经有统一边界，但逐工具的输出 Schema 和结果真实性校验还不完整。
3. 真实模型的多轮 Tool Calling、失败恢复和用户任务成功率还没有形成固定评测门禁。

## 3. 与主流 Runtime 的关键差异

主流实现通常把“对话线程”和“运行状态”分开：线程保存消息，RunState/Checkpoint 保存当前节点、工具调用、工具结果、审批中断和恢复游标。人工输入不是一条普通聊天消息，而是一个带类型和 payload 的 interrupt；恢复时使用同一个 thread/run 标识继续执行。

当前项目已经有同一 Run、`WAITING_USER`、审批续跑、缺信息续跑和基础检查点，但 `agent_run_states` 仍主要保存摘要哈希和展示进度，不能完全还原 Provider 的内部多轮消息。因此，应用重启后现在能可靠恢复已落库的业务动作和用户消息，但对“模型正在工具调用链中间崩溃”的场景仍是安全重试/重新生成，不是精确位置恢复。

主流实现还会把工具调用拆成可观测事件：模型轮次、工具开始、工具完成、工具失败、人工输入请求、人工输入回答、最终输出。当前项目已有第一阶段 Run Trace 和审计，但 ToolCallingAdvisor 内部轮次仍需要更细的事件桥接。

质量方面，不能只验证“接口返回 200”或“回答非空”。至少需要覆盖普通问答、资料组合、无资料边界、工具选择、工具参数、动作确认、补充信息、取消/改期、注入拒绝、重启恢复和多轮任务成功率。

## 4. 分阶段补缺方案

### P0：不改变普通聊天路径，先补运行正确性

1. **Structured Pending Interaction**
   - 为 `WAITING_USER` 统一保存 `type`、`requiredFields`、`actionId`、`notice` 和 schema 版本。
   - 缺信息、审批、选择候选、文件安全确认使用同一 pending 协议。
   - 前端默认仍只显示输入框和简短提示；高级详情才展示结构化状态。

2. **Model Turn Checkpoint**
   - 每个模型轮次保存安全的 request/response 元数据、tool call ID、工具版本、结果引用、attempt 和下一步游标。
   - 对含敏感正文的内容只保存加密或受限引用，不能把完整简历、报告和模型隐藏推理写入日志。
   - 恢复时优先消费已完成的幂等工具结果，禁止重复执行写操作。

3. **Tool Result Contract**
   - 给日程、简历、记忆、文件导入等写工具增加显式结果状态、动作 ID、影响范围和幂等键校验。
   - 模型只能依据服务端结果状态说“已生成草稿/已确认”，不能依据自然语言猜测成功。

### P1：提高质量和可运营性

1. **固定 Agent Eval Matrix**：把普通问答、报告引用、Skill+RAG 组合、上下文切换、日程创建/取消/改期、文件审核、提示注入、审批恢复、并发会话做成可重复样本。
2. **完整 Trace**：桥接模型内部轮次和基础设施 span，增加首 Token、总等待、工具耗时、重试原因和最终任务成功率。
3. **Evidence Envelope**：已为来源增加可选的 `sourceId/version/authority/selectedReason`，旧会话和旧构造保持兼容；回答引用仍只能引用本轮真实来源。后续补充跨来源冲突裁决和版本变更策略。
4. **Memory Governance**：已完成来源、置信度、过期和撤回标记，以及只注入有效记忆；后续补充 sourceId/version/authority 和可选恢复/审计视图。长期记忆只能作为参考，不覆盖本轮用户提供的事实。

### P2：有条件再扩展

1. **MCP Gateway**：先做 server/tool 白名单、OAuth scope、owner 映射、超时、限流、输出净化和审计，再接入外部工具。
2. **外部会议/日历**：先查询和生成草稿；创建、取消、发送邀请继续独立确认。
3. **有界子 Agent**：只有简历分析、知识研究或训练计划出现独立预算、权限和结果协议时再拆分，暂不引入自由协作式多 Agent。

## 5. 当前开发顺序

已完成并合入 Agent 开发总分支：

- 缺少日程信息时进入 `waiting_input`，补充消息复用同一 `runId`。
- Agent 工具契约的输入校验、硬超时、只读有限重试；写入草稿不自动重试。
- Skill 工具复用同一观测和执行契约。
- 上下文输入预算、Run Trace、审批续跑和基础重启恢复。

接下来按以下顺序推进，每一项单独分支、专项测试、全量后端回归、前端构建后再合入：

1. 结构化 pending interaction 和普通模型轮次 checkpoint。
2. 写工具结果 Schema/验证器与恢复契约测试。
3. 真实 Provider Agent 评测矩阵和多轮任务回归。
4. ToolCallingAdvisor 内部轮次 Trace 与基础设施耗时。
5. MCP Gateway 评估与最小只读接入（只有明确需要时）。

普通 Agent 的默认界面继续保持“输入问题—得到回答”；Loop、Trace、Token 和恢复状态只作为可展开的诊断信息，不把内部运行机制堆到主聊天路径。
