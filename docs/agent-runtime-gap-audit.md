# Agent Runtime 对照审计与补缺清单

## 1. 审计结论

审计日期：2026-11-08。

当前产品已经不是“只有一个聊天接口”的 Agent：它具备模型优先的意图路由、按能力裁剪工具、面试报告/简历/文件/RAG/Skill 的显式上下文、受控的 `knowledge_base_search` RAG 工具、有限 Agent Loop、动作草稿与人工确认、会话持久化、重启基础恢复、长期记忆、用量统计、审计和提示注入防护。

它目前更准确的定位是：**受控的单 Agent 业务运行时**，而不是自由探索式的多 Agent 系统。这个定位适合面试、简历、知识库和日程场景，也更容易保证“输入简单、结果可控、业务数据不被模型直接修改”。当前业务动作已经通过统一的 `agent_action_draft` 入口复用既有草稿/确认状态机，普通聊天仍不挂载该工具；只有识别到 RAG 能力时才暴露知识库检索工具。

对照主流 Agent Runtime 后，最大的差距不在“再增加几个按钮”，而在以下四件事：

1. 运行重启时可以安全重新生成，但还不能从 Provider 内部的精确模型轮次和 tool-call message 位置继续。
2. 工具结果已经有统一可信边界，但逐工具的领域输出 Schema 和结果真实性校验还不完整。
3. 真实模型的多轮 Tool Calling、失败恢复和用户任务成功率还没有形成固定评测门禁。
4. Trace 已能串起运行主链路，但 ToolCallingAdvisor 内部轮次、数据库/RAG/Redis span、首 Token 和排队等待仍不完整。

本轮补强了一处运行时一致性边界：生产环境的工具白名单现在优先由
`AgentToolRegistry` 的能力描述生成，路由器保留静态目录作为测试/迁移期兜底。这样新增或调整
工具时，工具名称、能力归属和风险目录不会再要求路由器同步维护第二份生产名单；普通对话仍拿到
空工具集，工具回调内部的 owner、意图、参数和确认校验不变。

## 3. 与主流 Runtime 的关键差异

### 3.1 按主流 Agent 产品的能力分层对照

这里的“主流”不是指某一家产品的页面样式，而是当前常见 Agent Runtime 都在强调的
几条工程基线：可恢复执行、结构化工具、人工审批、可观测 Trace、固定评测、受控记忆、
检索证据和外部连接授权。按这个基线看，当前项目的差距如下：

| 主流基线 | 当前项目 | 判断与补缺方向 |
| --- | --- | --- |
| Thread 与 Run 分离、可中断且可恢复 | 已有 Agent 会话、Run、WAITING_USER、Loop 检查点和安全重生成 | 已达到业务可用基线；还缺 Provider 内部消息/工具批次游标，精确续跑放 P1 |
| 工具是版本化、可校验、可授权的能力 | 已有动态工具目录、输入校验、结果契约、owner/幂等/确认；业务动作统一通过 `agent_action_draft` 生成待确认草稿 | 主要工具已覆盖；简历、记忆、训练任务和外部工具还要补更细的版本化输出 Schema 与细粒度权限 |
| 模型选择工具，但策略层可以否决 | 已有模型优先路由、规则兜底、工具白名单和回调二次校验 | 方向正确；需要通过真实 Provider 评测确认误选、漏选和参数错误率 |
| 高风险动作由 Human-in-the-loop 决定 | 日程、记忆、简历、训练等走草稿/确认，缺信息可暂停 | 已达到当前业务需要；候选选择、批量 pending 和外部发送仍需统一交互协议 |
| Trace 能看到模型轮次、工具、Guardrail 和业务阶段 | 已有 Run Trace、追加式模型/工具事件、摘要哈希、用量与费用；Provider response ID 和工具批次摘要已桥接到模型轮次；异步向量化状态也会以低敏事件关联原 Run | 仍需 ToolCallingAdvisor 内部消息、真实 Provider 失败原因、DB/RAG/Redis/队列 span，以及跨重启任务的最终对账指标 |
| Eval 不只看文本，还看任务成功、工具、grounding、安全和轨迹 | 已有离线行为矩阵、质量语料、RAG 评测和真实采集脚本；交互矩阵已扩展到 8 类，并覆盖通用会话的显式上下文隔离 | 仍需在候选环境固定执行，并把并发、断线、Provider 故障和副作用对账纳入门禁 |
| 记忆有写入策略、来源、过期和撤销 | 已有结构化轻量记忆、确认写入、来源/置信度/过期/撤销 | 适合当前产品；尚缺语义检索、冲突合并和用户可解释的“为什么记住”来源链 |
| RAG 具备权限、检索、引用和无答案边界 | 已有按需检索、来源权限、引用编号和无来源提示；新增受控 `knowledge_base_search` 工具，优先当前会话绑定知识库，只读取当前用户可访问且已完成向量化的知识库，并明确返回无来源/无命中状态；工具动态检索到的来源会进入本轮 grounding、证据评估、SSE 来源快照和 Run 持久化 | 目前是引用与元数据校验，不是事实级 claim-to-source 验证；混合检索/重排需按效果再做 |
| 外部连接有 Gateway、OAuth/Scope、限流和结果净化 | 当前没有 MCP Runtime/Gateway，会议能力仍是本地业务工具 | 不能直接挂外部 MCP；后续先做网关和权限，再接日历/会议/邮件 |
| 多 Agent 只在边界清晰时拆分 | 当前是受控单 Agent | 暂不拆分；先完成单 Agent 的恢复、评测和工具协议，避免复杂度空增 |

因此，当前实现与主流设计的差距主要是**生产化深度**而不是**架构方向错误**。不建议为了“看起来像 Agent”
立即加入自由多 Agent、自动执行外部写操作或把全部工具常驻挂给模型。

主流实现通常把“对话线程”和“运行状态”分开：线程保存消息，RunState/Checkpoint 保存当前节点、模型轮次、工具调用、工具结果、审批中断和恢复游标。人工输入不是一条普通聊天消息，而是一个带类型和 payload 的 interrupt；恢复时使用同一个 thread/run 标识继续执行。

当前项目已经有同一 Run、`WAITING_USER`、审批续跑、缺信息续跑、结构化 pending、模型轮次 checkpoint 和基础恢复。因此，应用重启后能恢复已落库的用户消息、Loop 计划、已完成动作和等待状态。剩余差距是 Provider 内部多轮消息/工具批次没有持久化，恢复时会安全地重新生成，而不是精确消费原始模型响应。

主流实现还会把工具调用拆成可观测事件：模型轮次、工具开始、工具完成、工具失败、人工输入请求、人工输入回答、最终输出。当前项目已有第一阶段 Run Trace 和审计，但 ToolCallingAdvisor 内部轮次仍需要更细的事件桥接。

质量方面，不能只验证“接口返回 200”或“回答非空”。固定评测至少要同时检查：工具是否选对、参数是否正确、RAG 是否有真实依据、是否拒绝越权和注入、等待/确认后任务是否最终成功、运行轨迹是否越界、重启后是否重复副作用。Google 的 Agent 评测建议也把工具使用、RAG grounding、安全、多轮任务成功率和轨迹质量作为独立维度：<https://google.github.io/agents-cli/guide/evaluation/>。

上下文和提示词方面，主流实践强调明确的约束、输出格式、示例以及把指令与资料分隔。当前项目的稳定前缀、资料边界和净化器已经覆盖基础安全要求；后续重点是让“来源冲突”和“没有依据”成为机器可观察状态，而不只依赖模型遵循提示：<https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices>。

## 4. 分阶段补缺方案

### P0：当前没有阻塞普通聊天的 P0 缺口

以下能力已经完成并合入 Agent 开发总分支，不应重复开发或改回旧路径：

- 通用 Agent 与面试复盘上下文隔离；报告必须显式绑定或明确请求。
- 模型优先组合路由、动态工具目录、稳定安全前缀、滚动摘要和输入预算。
- 有界 Agent Loop、模型/工具/Token/费用预算、超时和有限重试。
- 运行租约心跳与有效租约保护，避免恢复扫描误接管仍在等待模型或重试的运行。
- 结构化 pending interaction、同一 Run 的缺信息续跑和审批续跑。
- 模型轮次元数据 checkpoint、Loop 检查点和应用重启后的安全恢复。
- 工具输入/输出可信边界、owner/参数/幂等/确认校验和 Skill 观测桥接。
- RAG 能力按需暴露受控知识库检索工具；工具优先使用当前 Agent 会话绑定的知识库，没有命中或没有可用来源时不得声称使用了知识库；工具运行期间新增来源会回写本轮来源、grounding/证据评估和运行记录。
- 长期记忆的来源、置信度、过期和撤回治理；来源证据 envelope、冲突规则和运行结果质量门禁。

P0 不再新增功能。剩余的精确 Provider 续跑属于 P1：它提升恢复精度，但不应改变普通聊天和已完成的确认链路。

### P1：提高质量和可运营性

1. **真实 Provider 交互评测矩阵**：固定覆盖普通问题、隐式 Skill/RAG、报告绑定、简历/文件导入、训练动作草稿、创建/取消/改期、补充信息、确认/取消、连接断开恢复、并发会话和 Provider 失败切换；当前离线行为矩阵已覆盖 18 条路由/能力场景，包含自然表达动作与“如何操作”负例，真实模型多轮执行仍需在候选环境固定验收；同时校验最终任务状态、工具名/参数、pending 类型、Run 轨迹、证据评估、实际/估算 Token/耗时、动作结果契约和业务副作用；当前已增加补充/确认/取消的 Run 连续性和用户消息计数校验，采集低敏 `MODEL_TOOL_BATCH` 事件并校验模型轮次/工具数量、结果码/资源 ID 校验与提示注入不得触发工具的场景，并增加多实例租约接管与失联恢复验收。
2. **ToolCallingAdvisor 内部 Trace**：已有首个非空输出 Trace，以及工具真正开始执行和逻辑调用完成/失败事件；追加式 Run 事件已记录模型轮次、Run 内 tool-call ID、工具名、参数/结果摘要哈希、Provider response ID、Provider 工具批次摘要和状态，可按 owner/session/run 查询；仍需在真实 Provider/Advisor 边界补充内部消息批次、失败原因和更完整 usage，并接入数据库/RAG/Redis/队列的低敏 span；不记录 Prompt 正文和隐藏推理。
3. **工具领域输出 Schema**：资源动作结果已补充统一顶层状态、operation 和 assetId；日程创建/取消/修改结果已校验状态、说明、动作类型和候选 ID；面试搜索、上下文列表、绑定/清除已增加领域结果校验；统一业务动作草稿已覆盖训练计划、练习题、训练任务、记忆、简历编辑、报告导出和面试改名，并通过 `agent-action.v2` 校验版本、确认标记、影响范围、资源作用域、operation、actionId、会话身份、风险级别和领域 toolId；文件上下文动作新增 `agent-context-asset.v1`，知识库导入明确区分 `ASYNC_JOB_SUBMITTED` 与 `ASYNC_JOB_FAILED`，并要求知识库 ID/失败说明；知识库向量化现在有 `agent_async_operations` 和 `ASYNC_OPERATION_*` Run 事件，能把提交状态与真实 KB 状态关联；后续继续补齐各领域执行后的真实结果结构和历史任务对账。

## 5. 当前开发顺序

已完成并合入 Agent 开发总分支：

- 多会话、上下文显式绑定、稳定前缀、历史摘要和输入预算。
- 模型优先组合路由、有限 Loop、Tool Calling、工具契约和资源预算。
- 缺少日程信息时进入 `waiting_input`，补充消息复用同一 `runId`；审批也复用原 Run。
- Loop/模型轮次/工具/来源/用量/审计的持久化基础，记忆撤回、证据元数据和运行结果质量门禁。
- Agent 工具异常提示单位修复，避免把 Token 预算显示为“调用次数”。
- 统一业务动作草稿入口已覆盖训练计划、练习题、训练任务、长期记忆、简历编辑、报告导出和面试改名；普通聊天仍保持无工具路径。

接下来按以下顺序推进，每一项单独分支、专项测试、全量后端回归、前端构建后再合入：

1. 真实 Provider 交互评测矩阵和候选环境低风险验收。
2. ToolCallingAdvisor 内部轮次 Trace、工具批次与基础设施耗时。追加式 Run 事件已完成第一阶段，仍需真实 Provider 契约验证。
3. 日程/简历/记忆/文件工具的领域输出 Schema 和结果校验；统一动作草稿入口已完成基础契约，后续只补各领域更细的版本化结果。
4. 结构化证据冲突、无依据和来源版本变化事件。来源完整性低敏状态已接入 Trace；仍需补事实级冲突与“结论—证据”关联。
5. 精确 tokenizer 预算与缓存/裁剪指标。
6. MCP Gateway、外部日历或有界子 Agent，仅在业务确实需要时立项。

普通 Agent 的默认界面继续保持“输入问题—得到回答”；Loop、Trace、Token 和恢复状态只作为可展开的诊断信息，不把内部运行机制堆到主聊天路径。
