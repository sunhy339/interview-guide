# Agent Runtime 对照审计与补缺清单

## 1. 审计结论

审计日期：2026-11-07。

当前产品已经不是“只有一个聊天接口”的 Agent：它具备模型优先的意图路由、按能力裁剪工具、面试报告/简历/文件/RAG/Skill 的显式上下文、有限 Agent Loop、动作草稿与人工确认、会话持久化、重启基础恢复、长期记忆、用量统计、审计和提示注入防护。

它目前更准确的定位是：**受控的单 Agent 业务运行时**，而不是自由探索式的多 Agent 系统。这个定位适合面试、简历、知识库和日程场景，也更容易保证“输入简单、结果可控、业务数据不被模型直接修改”。

对照主流 Agent Runtime 后，最大的差距不在“再增加几个按钮”，而在以下四件事：

1. 运行重启时可以安全重新生成，但还不能从 Provider 内部的精确模型轮次和 tool-call message 位置继续。
2. 工具结果已经有统一可信边界，但逐工具的领域输出 Schema 和结果真实性校验还不完整。
3. 真实模型的多轮 Tool Calling、失败恢复和用户任务成功率还没有形成固定评测门禁。
4. Trace 已能串起运行主链路，但 ToolCallingAdvisor 内部轮次、数据库/RAG/Redis span、首 Token 和排队等待仍不完整。

## 3. 与主流 Runtime 的关键差异

主流实现通常把“对话线程”和“运行状态”分开：线程保存消息，RunState/Checkpoint 保存当前节点、模型轮次、工具调用、工具结果、审批中断和恢复游标。人工输入不是一条普通聊天消息，而是一个带类型和 payload 的 interrupt；恢复时使用同一个 thread/run 标识继续执行。

当前项目已经有同一 Run、`WAITING_USER`、审批续跑、缺信息续跑、结构化 pending、模型轮次 checkpoint 和基础恢复。因此，应用重启后能恢复已落库的用户消息、Loop 计划、已完成动作和等待状态。剩余差距是 Provider 内部多轮消息/工具批次没有持久化，恢复时会安全地重新生成，而不是精确消费原始模型响应。

主流实现还会把工具调用拆成可观测事件：模型轮次、工具开始、工具完成、工具失败、人工输入请求、人工输入回答、最终输出。当前项目已有第一阶段 Run Trace 和审计，但 ToolCallingAdvisor 内部轮次仍需要更细的事件桥接。

质量方面，不能只验证“接口返回 200”或“回答非空”。固定评测至少要同时检查：工具是否选对、参数是否正确、RAG 是否有真实依据、是否拒绝越权和注入、等待/确认后任务是否最终成功、运行轨迹是否越界、重启后是否重复副作用。Google 的 Agent 评测建议也把工具使用、RAG grounding、安全、多轮任务成功率和轨迹质量作为独立维度：<https://google.github.io/agents-cli/guide/evaluation/>。

上下文和提示词方面，主流实践强调明确的约束、输出格式、示例以及把指令与资料分隔。当前项目的稳定前缀、资料边界和净化器已经覆盖基础安全要求；后续重点是让“来源冲突”和“没有依据”成为机器可观察状态，而不只依赖模型遵循提示：<https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices>。

## 4. 分阶段补缺方案

### P0：当前没有阻塞普通聊天的 P0 缺口

以下能力已经完成并合入 Agent 开发总分支，不应重复开发或改回旧路径：

- 通用 Agent 与面试复盘上下文隔离；报告必须显式绑定或明确请求。
- 模型优先组合路由、动态工具目录、稳定安全前缀、滚动摘要和输入预算。
- 有界 Agent Loop、模型/工具/Token/费用预算、超时和有限重试。
- 运行租约心跳与有效租约保护，避免恢复扫描误接管仍在等待模型或重试的运行。
- 结构化 pending interaction、同一 Run 的缺信息续跑和审批续跑。
- 模型轮次元数据 checkpoint、Loop 检查点和应用重启后的安全恢复。
- 工具输入/输出可信边界、owner/参数/幂等/确认校验和 Skill 观测桥接。
- 长期记忆的来源、置信度、过期和撤回治理；来源证据 envelope、冲突规则和运行结果质量门禁。

P0 不再新增功能。剩余的精确 Provider 续跑属于 P1：它提升恢复精度，但不应改变普通聊天和已完成的确认链路。

### P1：提高质量和可运营性

1. **真实 Provider 交互评测矩阵**：固定覆盖普通问题、隐式 Skill/RAG、报告绑定、简历/文件导入、创建/取消/改期、补充信息、确认/取消、连接断开恢复、并发会话和 Provider 失败切换；同时校验最终任务状态、工具名/参数、pending 类型、Run 轨迹、Token/耗时和业务副作用；当前已增加补充/确认/取消的 Run 连续性和用户消息计数校验，并增加多实例租约接管与失联恢复验收。
2. **ToolCallingAdvisor 内部 Trace**：已有首个非空输出 Trace，以及工具真正开始执行和逻辑调用完成/失败事件；继续记录每个模型轮次、tool-call ID、工具批次、失败原因和 usage，接入数据库/RAG/Redis/队列的低敏 span，并增加总等待、重试原因和最终任务成功率；不记录 Prompt 正文和隐藏推理。
3. **工具领域输出 Schema**：资源动作结果已补充统一顶层状态、operation 和 assetId；日程创建/取消/修改结果已校验状态、说明、动作类型和候选 ID；继续为简历导入、记忆写入、文件入库定义版本化结果结构，并校验真实状态、actionId、owner、幂等键和影响范围。
4. **证据冲突和无依据状态**：已增加来源元数据完整性事件，可记录旧来源元数据、重复引用、来源版本冲突和权限来源冲突；仍需把报告与当前用户说法冲突、RAG 无命中、来源版本变化与事实级证据关联写成更完整的结构化事件，避免只依赖模型遵循固定提示。
5. **上下文预算精度**：保留字符预算作为安全兜底；在 Provider 支持时增加 tokenizer 估算，区分应用摘要、实际输入/输出 Token、缓存命中和裁剪原因。

### P2：有条件再扩展

1. **MCP Gateway**：先做 server/tool 白名单、OAuth scope、owner 映射、超时、限流、输出净化和审计，再接入外部工具。
2. **外部会议/日历**：先查询和生成草稿；创建、取消、发送邀请继续独立确认。
3. **有界子 Agent**：只有简历分析、知识研究或训练计划出现独立预算、权限和结果协议时再拆分，暂不引入自由协作式多 Agent。

## 5. 当前开发顺序

已完成并合入 Agent 开发总分支：

- 多会话、上下文显式绑定、稳定前缀、历史摘要和输入预算。
- 模型优先组合路由、有限 Loop、Tool Calling、工具契约和资源预算。
- 缺少日程信息时进入 `waiting_input`，补充消息复用同一 `runId`；审批也复用原 Run。
- Loop/模型轮次/工具/来源/用量/审计的持久化基础，记忆撤回、证据元数据和运行结果质量门禁。
- Agent 工具异常提示单位修复，避免把 Token 预算显示为“调用次数”。

接下来按以下顺序推进，每一项单独分支、专项测试、全量后端回归、前端构建后再合入：

1. 真实 Provider 交互评测矩阵和候选环境低风险验收。
2. ToolCallingAdvisor 内部轮次 Trace、工具批次与基础设施耗时。
3. 日程/简历/记忆/文件工具的领域输出 Schema 和结果校验。
4. 结构化证据冲突、无依据和来源版本变化事件。来源完整性低敏状态已接入 Trace；仍需补事实级冲突与“结论—证据”关联。
5. 精确 tokenizer 预算与缓存/裁剪指标。
6. MCP Gateway、外部日历或有界子 Agent，仅在业务确实需要时立项。

普通 Agent 的默认界面继续保持“输入问题—得到回答”；Loop、Trace、Token 和恢复状态只作为可展开的诊断信息，不把内部运行机制堆到主聊天路径。
