# Agent 需求发散审查

审查日期：2026-11-05

这份记录用于检查“做一个 Agent 功能”是否只实现了表面入口，还是已经覆盖上下文、会话、动作、安全、恢复和验收闭环。

## 当前已闭环

- 通用 Agent 与面试复盘会话隔离；未显式选择面试报告时不会自动读取报告。
- 输入区可以显式添加简历、面试报告、文件和知识库上下文；上传文件先审核，疑似提示注入需要额外确认。
- 会话消息、运行状态、Loop 进度、来源、用量和失败状态持久化；SSE 断开可以通过后台状态恢复。
- 最近消息裁剪前有确定性摘要，固定系统前缀有版本和指纹，动态资料不会污染稳定前缀。
- Agent Loop 是有上限的单 Agent 受控循环，不允许无限调用工具；Skill、RAG、长期记忆和工具结果都按不可信资料边界注入。
- 写操作统一生成 `PROPOSED` 动作，经过 owner 校验、幂等、确认、执行、失败重试和审计；不会直接覆盖面试报告、简历原文件或知识库。
- 面试日程目前支持创建、修改/改期和取消：请求进入正常 Agent 会话；修改和取消都会结合当前消息、显式日程 ID/原时间及用户自己的日程候选，唯一候选才生成动作，多候选要求选择。
- 普通学习/问答不会因为路径带有面试会话 ID 就自动读取面试报告；最终回答统一使用受控 Agent 客户端，由主模型决定是否调用 Skill、RAG、MCP 或业务工具，没有明确资料/业务意图时通常直接回答。
- Agent 请求在上下文组装前先由当前 Provider 的无工具模型调用 `AgentIntentRouter` 做模式辅助判断；它只帮助决定是否进入主面试报告上下文，不再把 `SKILL`、`RAG`、`CONTEXT`、`INTERVIEW_REPORT` 和 `SCHEDULE` 做成互斥工具白名单。最终回答统一进入受控 Agent ChatClient，主模型可自主选择零个、一个或多个工具并连续处理结果；识别到 RAG 能力时才暴露受控 `knowledge_base_search`，优先当前会话绑定知识库，工具回调继续负责 owner、参数、意图和确认校验。原有上下文组装和稳定前缀不因路由增强而改变。分类调用计入本次运行的模型调用、Token 和费用统计。
- Agent 页面支持多会话、刷新恢复、输入草稿缓存、动作管理、长期记忆管理和用量/活动筛选。

## 发现的边界和未完成项

### 1. “面试会议”目前是本地日程，不是外部会议

当前可以创建和取消应用内 `interview_schedule` 记录，但不会自动创建飞书、腾讯会议、Zoom 房间，也不会发送日历邀请。要做成真正的会议助手，需要：

- 外部日历/会议服务 OAuth 和账号绑定；
- 创建、更新、取消、冲突查询和邀请发送的权限模型；
- 外部事件 ID、同步状态、失败重试、撤销和 webhook 对账；
- 将第三方连接器包在本地 owner、确认、幂等和审计边界内。

这是独立扩展，不应在没有账号授权和接口选择时假装已经完成。

### 2. 日程修改/改期已完成首版，但仍需完善变更审计

已增加 `schedule.update_draft` 和 `interview.schedule.update` 动作链路，支持“改到明天下午三点”“换面试链接”“修改面试官”等请求。当前仍需继续完善：

- 先按会话历史或显式日程 ID找到唯一原日程；
- 展示变更前后差异；
- 用户确认后更新，并保留变更审计；
- 处理并发修改、已完成/已取消状态和重复请求；
- 为已确认修改提供可撤销或恢复信息。

### 3. 取消动作有确认，但还没有 Agent 内“撤销取消”闭环

取消会保留历史记录，但当前恢复状态仍主要依赖面试日程页面。若要让 Agent 真正承担事务，需要增加 `schedule.restore_draft` 或统一的变更历史/撤销动作，避免只实现“能写、不能撤销”。

### 4. 当前工具是应用内工具，不是 MCP 生态接入

Skill、RAG 和日程工具已经能支撑面试教练，但暂未接入 MCP Server/Client。MCP 不应为了“看起来完整”而加入；只有需要跨系统访问日历、招聘系统、邮件或企业知识库时再作为适配层引入，并复用本地安全边界。

### 5. 真实环境验收仍需覆盖动作闭环

本地自动化已覆盖工具意图、权限边界、会话隔离、恢复、日程草稿和前端回归；候选环境已部署并完成启动/资源版本核验。真实模型验收还应补充一组低风险闭环：

1. 创建一条候选环境日程；
2. 用同一 Agent 会话以“取消刚才那个面试”发起请求；
3. 验证模型结合历史调用取消草稿工具；
4. 验证多候选时不误选；
5. 点击确认后验证状态为 `CANCELLED`，刷新页面消息和活动记录仍存在；
6. 重复确认、跨用户 ID、已完成日程和连接中断均验证拒绝或幂等。

## 结论

当前 Agent 的“输入—理解上下文—调用受控工具—生成待确认动作—确认执行—持久化—审计/恢复”主链路已经成立，最近补上的取消能力也不再是单句正则功能。

真正需要继续发散的方向不是继续堆更多按钮，而是围绕每个工具补齐：

```text
识别 -> 历史消歧 -> 权限 -> 预览 -> 确认 -> 幂等 -> 执行
-> 失败恢复 -> 审计 -> 撤销/对账 -> 真实验收
```

因此后续优先级为：

1. 完成真实候选环境的创建/取消/多候选/恢复验收；
2. 增加日程改期/修改动作；
3. 设计外部日历/会议连接器后再决定 MCP；
4. 继续把每个 Agent 工具按同一闭环扩展，而不是单独增加孤立入口。
