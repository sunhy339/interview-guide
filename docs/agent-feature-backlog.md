# Agent 功能分阶段清单

更新日期：2026-11-07

这份清单用于控制 Agent 后续开发范围。每个功能都从当前开发总分支创建独立
`feature/*` 分支，专项测试和全量回归通过后才能合入；未验收的真实 Provider
能力不标记为完成。

## 已完成：P0 运行正确性与兼容边界

| 能力 | 当前状态 | 兼容边界 |
| --- | --- | --- |
| 通用 Agent 与面试复盘隔离 | 已完成 | 只有显式绑定或明确请求才读取面试报告 |
| 上下文和稳定前缀 | 已完成 | 报告、简历、文件、Skill、RAG 作为不可信资料；保留滚动摘要和预算裁剪 |
| 受控 Agent Loop | 已完成 | 有模型、工具、Token、费用、超时和重试预算，不引入自由多 Agent |
| Tool Calling 与动作确认 | 已完成 | 写操作先生成草稿；确认、拒绝、补充信息复用原 Run |
| 提示注入与 owner 隔离 | 已完成 | 工具边界再次校验用户意图、owner、参数和结果可信边界 |
| 长期记忆治理 | 已完成 | 默认只读；写入需草稿和确认；支持来源、置信度、过期和撤回 |
| 运行恢复基础层 | 已完成第一阶段 | 会话、RunState、租约、审批续跑和已完成动作可恢复；不重复执行已提交副作用 |
| 模型与工具低敏 Trace | 已完成第一阶段 | 记录 `modelTurnId`、Run 内 `toolCallId` 和开始/完成/失败事件，不记录正文或隐藏推理 |
| 日程工具结果契约 | 已完成第一阶段 | 校验状态、说明、动作类型和多候选 ID，不改变创建/取消/修改确认链路 |
| 默认交互路径 | 已完成代码收敛 | 主路径保持“输入问题—得到回答”；Loop、Trace、用量只作为诊断信息 |

## 当前推进：P1 质量和可运营性

### P1.1 真实 Provider 多轮交互评测

覆盖普通问答、Skill+RAG 组合、显式面试报告、文件审核、日程创建/取消/修改、
缺信息补充、确认/拒绝、连接中断恢复、并发会话和 Provider 失败切换。

验收不仅看 HTTP 成功，还要核对：

- 最终会话状态和 pending 类型；
- 工具名称、关键参数和动作状态；
- Run 是否连续、用户消息是否重复；
- Trace 动作、Token、耗时和费用；
- 数据库实际副作用是否只发生一次。

当前已有离线矩阵和 fixture 门禁，真实 Provider 样本仍待在目标环境执行。

### P1.2 Durable RunState 与内部轮次

补齐 ToolCallingAdvisor 内部模型消息、provider tool-call ID、tool-call batch、
结构化工具结果和等待状态的可恢复检查点。目标是区分：

```text
未执行 -> 执行中 -> 成功但未落状态 -> 等待用户 -> 已完成/失败
```

第一阶段允许安全重新生成；精确恢复前必须先解决重复副作用、跨实例租约和版本兼容，
因此不能直接替换当前安全恢复路径。

### P1.3 领域结果契约

日程工具第一阶段校验已完成；统一业务动作入口 `agent_action_draft` 已增加 `agent-action.v2`
结果契约，明确版本、状态、人工确认标记、影响范围、面试资源作用域、动作 ID、Agent 会话、
风险级别和领域 `toolId`。当前覆盖训练计划、练习题、训练任务、记忆、简历编辑、报告导出和面试改名。
执行结果契约 `agent-action.result.v1` 已落库并返回前端，覆盖训练任务、记忆写入、简历编辑、简历导入、
报告导出、面试改名和日程创建/取消/修改；服务端会校验结果码、影响类型、资源类型和资源 ID，审批续跑
也会携带这组低敏结构化结果。模型只能根据服务端可信结果声明业务状态，不能根据自然语言猜测“已完成”。
真实交互采集器和动作验收脚本已把结果契约字段纳入门禁，确认/取消动作缺少真实资源 ID 会直接失败。
后续仍需为文件入库、知识库向量化等异步动作补充任务状态、幂等键、真实影响范围和完成后对账。

### P1.4 证据与无依据状态

保留现有来源编号和 grounding 检查，继续增加：

- RAG 无命中、来源版本变化、来源互相冲突的结构化事件；
- 回答引用的来源集合和未引用来源数量；
- “没有足够证据”与“来源校验失败”的不同状态；
- 评测中对引用存在性和事实正确性的分离判断。

来源编号校验不等于事实级语义验证，不能把两者混为一个成功状态。

### P1.5 精确预算与成本可见性

当前字符预算是安全兜底，不是精确 Token 计量。后续在 Provider 支持时增加 tokenizer
估算，并分别统计应用摘要、实际 Prompt/Completion Token、裁剪原因、重试消耗和缓存命中。
任何预算增强都不能重新引入单次 Provider `max-output-tokens` 的硬限制。

## 后置：P2 外部能力

1. **MCP Gateway**：先做 Server/Tool 白名单、OAuth/Scope、owner 映射、超时、限流、
   输出净化和审计，再允许外部工具进入 Agent；外部写操作仍走本地草稿和确认。
2. **外部日历和会议**：先支持查询和草稿，真正创建、取消、改期、发送邀请必须单独确认。
3. **有界子 Agent**：只有当简历分析、知识研究或训练计划具备独立上下文、预算、权限和
   结果 Schema 时才拆分，不引入自由协作式多 Agent 网络。

## 每个功能的统一完成门槛

1. 从开发总分支创建独立 `feature/*` 分支，写清接口、状态和兼容边界。
2. 增加正常、失败、超时、重试、刷新、重启、并发、权限和副作用测试。
3. 通过专项测试、Agent 相关全量后端回归、前端 TypeScript 编译和 Vite 构建。
4. 涉及真实模型、队列、数据库或外部服务时，再执行真实环境验收；fixture 不能替代真实验收。
5. 只合入开发总分支，不自动推送、部署或修改 `master`。
6. 保留旧 API、旧面试/简历/RAG/Skill/日程流程；新增能力默认不改变普通聊天路径。

## 当前建议顺序

```text
真实 Provider 评测
        ↓
内部模型/工具批次 Trace 与恢复
        ↓
简历/记忆/文件领域结果契约
        ↓
证据冲突与无依据事件
        ↓
Tokenizer/缓存预算
        ↓
MCP Gateway / 外部日历 / 有界子 Agent
```
