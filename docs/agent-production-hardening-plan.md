# Agent 生产化完善分阶段计划

## 1. 目标

在保留现有面试、简历、RAG、Skill、日程和 Agent 会话能力的前提下，逐步把当前业务型单 Agent 完善为可恢复、可审计、可扩展的 Agent Runtime。

本计划不以引入多 Agent 或大量新工具为目标，优先解决执行正确性、状态恢复、人工确认、上下文边界和回归风险。

## 2. 已有能力基线

- 通用 Agent 与面试复盘已经分离，面试报告需要显式绑定或明确请求才能进入上下文。
- 意图识别采用模型优先、规则兜底；Skill、RAG、面试报告和上下文资料可以组合使用。
- 已有上下文资产审核、提示注入防护、owner 隔离、动作确认、审计、用量统计和 Provider 失败切换。
- 已有有限 Loop、滚动摘要、前缀指纹、任务进度持久化和应用重启后的基础恢复。
- 已有简历导入、日程创建/取消/修改、训练任务和长期记忆动作草稿能力。

## 3. P0：运行正确性与数据安全

### P0.1 上下文编排只读化

状态：已完成代码修改和专项、全量后端回归；待功能验收后合入。

- 上下文构建只调用长期记忆 `load`，不能隐式调用 `remember`。
- 普通对话、打开面试报告和刷新页面不能改变跨会话长期记忆。
- 记忆写入必须沿用动作草稿和用户确认链路。

验收：普通问题、面试复盘和上下文刷新均不会产生记忆写入；明确确认记忆动作仍然可以写入。

### P0.2 统一 Agent RunState

当前进度：已完成第一步兼容增量和 RunState 基础层。业务动作草稿会保存产生它的 `runId`，工具审计也复用同一运行代次；新增独立 `agent_run_states` 检查点表，记录阶段、步骤、工具参数/结果摘要哈希、审批待处理标志、上下文版本、尝试次数、租约和心跳。旧接口和历史动作允许为空，幂等键不包含 `runId`。目前还没有把审批确认接成原运行续跑，也没有替代现有会话表的恢复主逻辑。

新增统一的运行状态模型，至少保存：

```text
runId、agentSessionId、phase、stepIndex、toolCallId、toolName
toolArgumentsHash、toolResultReference、pendingApproval
contextVersion、attempt、lease、heartbeat、status
```

要求：

- 状态按步骤持久化，不能只保存自由文本计划和展示轨迹。
- 每一步有稳定的幂等键和执行尝试号。
- 任务恢复时能够区分“未执行、执行中、执行成功但状态未落库、需要人工确认”。
- 不改变现有消息表和旧会话接口，先通过新增字段或独立运行状态表兼容接入。

### P0.3 通用人工确认与恢复

当前进度：已完成第一阶段兼容接入。带 `runId` 的动作在生成后会把运行标记为 `WAITING_USER`，前端可以明确展示等待确认；动作确认成功、重试成功或用户取消后，会收束原运行。历史动作仍不带运行关联，继续沿用旧流程。当前还没有把审批结果再次送回模型执行新的模型轮次，下一阶段继续补齐真正的 RunState resume。

- 将动作确认提升为运行级 `WAITING_USER` 状态。
- 用户确认、拒绝或编辑后，恢复原 Agent Run，而不是只执行一条孤立动作。
- 支持缺少信息时暂停等待用户补充。
- 刷新页面、应用重启后仍显示待处理请求，并能继续原流程。

### P0.4 通用 Tool Calling Loop

统一为：

```text
模型决策 -> 策略检查 -> 工具执行 -> 工具结果净化
       -> 回传模型 -> 再决策 / 等待确认 / 完成
```

- 读工具和写工具都使用统一的工具执行协议。
- Provider 不支持 Tool Calling 续调用时，使用服务端兼容适配器兜底。
- 每轮受最大步骤、最大模型调用、最大工具调用、超时和费用预算限制。
- 工具结果必须经过验证，不能仅凭模型生成的文字宣称动作成功。

## 4. P1：上下文、工具和质量工程

### P1.1 Context Envelope 与结构化摘要

- 以 Token 预算为主、字符预算为安全兜底。
- 摘要按“已确认事实、决定、待办、用户偏好、当前上下文、来源”组织。
- 保存摘要覆盖的消息序号、版本和上下文快照版本。
- 动态裁剪工具 Schema，普通问题不发送不需要的工具定义。
- 区分应用自己的摘要和 Provider Prompt Cache；分别统计缓存命中和上下文压缩。

### P1.2 工具注册与策略中心

每个工具统一声明：

- 稳定名称、版本、输入 Schema 和输出 Schema；
- 只读/草稿/写入风险等级；
- 所需权限、是否需要人工确认；
- 超时、重试、幂等策略和结果验证器；
- 允许的会话范围和资源类型。

现有工具先适配到注册中心，再逐步增加工具，不改变已有 API 和动作状态机。

### P1.3 RAG 和 Skill 增强

- RAG 增加混合召回、重排、来源级权限和回答级引用。
- 增加检索命中、引用正确性、无答案拒答和答案 grounding 评测。
- Skill 增加版本、启用状态、适用范围和变更审计。
- 普通问题只有在模型判断确实需要时才加载 Skill 或 RAG。

### P1.4 可观测性和测试

- 为一次 Agent Run 建立统一 Trace ID，串联分类、规划、模型、工具、数据库、Redis 和恢复任务。
- 记录首 Token 延迟、队列时间、各阶段耗时、工具成功率、恢复次数、Token 和费用。
- 增加真实 Provider 契约测试、多轮 Tool Calling、审批恢复、崩溃恢复、并发会话和失败注入测试。
- 增加固定 Agent 评测集，并将工具正确性、安全拒绝、上下文引用和回答质量纳入回归门槛。

## 5. P2：外部连接和可选扩展

### P2.1 MCP Gateway

当前仓库只有 MCP 相关 Skill 资料，没有实际 MCP Runtime。后续接入时必须经过本地 Gateway：

- Server 白名单和工具白名单；
- OAuth、Scope 和最小权限；
- owner 映射、超时、限流、输出大小和审计；
- 外部结果统一视为不可信资料；
- 外部写操作继续使用本地草稿、确认、幂等和回滚策略。

### P2.2 外部会议和日历

先支持读取和草稿，之后再接入 OAuth/API：

- 日历查询；
- 飞书、腾讯会议、Zoom 等会议创建；
- 邮件或日历邀请草稿；
- 发送操作必须单独确认，不能因为“安排面试”直接发送外部消息。

### P2.3 有界子 Agent

只有当单 Agent 的上下文或任务复杂度确实达到瓶颈时，才增加简历分析器、RAG 研究器等有界子 Agent。子 Agent 必须拥有独立预算、权限、上下文和结果 Schema，不做自由协作式多 Agent 网络。

## 6. 不影响现有功能的约束

- 不修改原始面试报告、评分、回答和上传简历；所有变更继续使用独立草稿或新文件。
- 不改变旧面试详情进入 Agent 的兼容接口。
- 不让 Skill、RAG、文件或工具结果获得系统指令权限。
- 不让模型直接写业务表；写入必须经过服务端 owner、参数、状态、幂等和确认校验。
- 新功能默认关闭或只对新通用会话生效，旧会话保留原行为。
- 每个功能使用独立 `feature/*` 分支，先通过专项测试，再跑 Agent 相关回归和前端构建，最后合入 `develop-agent`。
- 未通过真实环境验收前不发布正式环境，不修改 `master`。

## 7. 每项功能的完成标准

1. 有明确的接口、状态和兼容边界。
2. 有正常、失败、重试、刷新、重启、并发和权限测试。
3. 旧面试、简历、RAG、Skill 和日程主流程回归通过。
4. 前端默认路径保持输入简单、结果清晰，内部 Loop 详情只作为高级诊断信息。
5. 能说明 Token、耗时、失败原因、恢复状态和是否产生业务副作用。
