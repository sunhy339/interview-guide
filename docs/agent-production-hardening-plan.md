# Agent 生产化完善分阶段计划

## 1. 目标

在保留现有面试、简历、RAG、Skill、日程和 Agent 会话能力的前提下，逐步把当前业务型单 Agent 完善为可恢复、可审计、可扩展的 Agent Runtime。

本计划不以引入多 Agent 或大量新工具为目标，优先解决执行正确性、状态恢复、人工确认、上下文边界和回归风险。

## 2. 已有能力基线

- 通用 Agent 与面试复盘已经分离，面试报告需要显式绑定或明确请求才能进入上下文。
- 意图识别采用模型优先、规则兜底；Skill、RAG、面试报告和上下文资料可以组合使用。
- 已有上下文资产审核、提示注入防护、owner 隔离、动作确认、审计、用量统计和 Provider 失败切换。
- 已有有限 Loop、滚动摘要、前缀指纹、任务进度持久化和应用重启后的基础恢复。
- 已有简历导入、日程创建/取消/修改、训练任务和长期记忆动作草稿能力。
- 长期记忆条目已具备来源、置信度、过期和撤回边界；撤回/过期条目保留在存储治理数据中，但不会回流到 Agent 上下文。
- Agent 来源摘要已增加可选的 `sourceId/version/authority/selectedReason`，用于后续证据追踪和冲突裁决；旧会话来源仍可正常读取。

## 3. P0：运行正确性与数据安全

### P0.1 上下文编排只读化

状态：已完成代码修改、专项和全量后端回归，并已合入 Agent 开发总分支；待真实环境功能验收。

- 上下文构建只调用长期记忆 `load`，不能隐式调用 `remember`。
- 普通对话、打开面试报告和刷新页面不能改变跨会话长期记忆。
- 记忆写入必须沿用动作草稿和用户确认链路。

验收：普通问题、面试复盘和上下文刷新均不会产生记忆写入；明确确认记忆动作仍然可以写入。

### P0.2 统一 Agent RunState

当前进度：已完成第一阶段兼容增量和 RunState 基础层。业务动作草稿会保存产生它的 `runId`，工具审计也复用同一运行代次；新增独立 `agent_run_states` 检查点表，记录阶段、步骤、工具参数/结果摘要哈希、审批待处理标志、上下文版本、尝试次数、租约和心跳。模型等待或重试期间会刷新运行租约，恢复扫描发现有效租约时不会接管，租约读取失败则保守跳过接管。审批续跑已经复用原 `runId`，并增加 `resume_action_id` 恢复标记；应用在事务提交与事件监听器之间崩溃时，启动恢复会读取已完成动作结果，只恢复模型回答，不重放原写操作。旧接口和历史动作允许为空。仍未达到完整 Durable RunState：模型轮次、工具结果正文/结构化 pending batch 仍未持久化。

新增统一的运行状态模型，至少保存：

```text
runId、agentSessionId、phase、stepIndex、toolCallId、toolName
toolArgumentsHash、toolResultReference、pendingApproval
contextVersion、attempt、lease、heartbeat、status
```

要求：

- 状态按步骤持久化，不能只保存自由文本计划和展示轨迹。
- 每一步有稳定的幂等键和执行尝试号。
- 任务恢复时能够区分“未执行、执行中、执行成功但状态未落库、需要人工确认”。
- 不改变现有消息表和旧会话接口，先通过新增字段或独立运行状态表兼容接入。

### P0.3 通用人工确认与恢复

当前进度：已完成同一 Run 的第一阶段恢复。带 `runId` 的动作在生成后会把运行标记为 `WAITING_USER`；动作确认成功、重试成功或用户取消后，会创建新的助手续答载体，将动作结果作为系统事件送回原会话，复用原 `runId` 继续生成。缺少日程信息时也会进入 `waiting_input`，下一条补充消息复用原 `runId`，并将原始请求与补充内容交给受控工具参数解析。审批事务会先落 `resume_pending` 标记，应用重启恢复时按动作 ID读取成功/取消结果，避免重复执行原工具。仍需补齐通用结构化 pending batch 和模型轮次本身的完整持久化。

- 将动作确认提升为运行级 `WAITING_USER` 状态。
- 用户确认、拒绝或编辑后，恢复原 Agent Run，而不是只执行一条孤立动作。
- 支持缺少信息时暂停等待用户补充。
- 刷新页面、应用重启后仍显示待处理请求，并能继续原流程。

### P0.4 通用 Tool Calling Loop

统一为：

```text
模型决策 -> 策略检查 -> 工具执行 -> 工具结果净化
       -> 回传模型 -> 再决策 / 等待确认 / 完成
```

- 读工具和写工具都使用统一的工具执行协议。
- Provider 不支持 Tool Calling 续调用时，使用服务端兼容适配器兜底。
- 每轮受最大步骤、最大模型调用、最大工具调用、总 Token、可选费用预算和超时限制；总 Token/费用预算只阻止下一次模型调用，不设置 Provider 单次输出上限。
- 工具结果必须经过验证，不能仅凭模型生成的文字宣称动作成功。

## 4. P1：上下文、工具和质量工程

### P1.1 Context Envelope 与结构化摘要

- 当前进度：已完成第一阶段动态工具目录裁剪，并增加模型调用前的可配置输入预算。普通
  问答不再默认挂载业务工具或 Skill；CONTEXT/INTERVIEW_REPORT、SKILL 和 SCHEDULE 能力按
  意图组合加载对应工具族。当前预算使用保守字符估算，只裁剪历史与资料，不设置 Provider
  输出上限；精确 tokenizer、RAG 按需检索和 Provider Prompt Cache 统计仍待后续实现。

- 以 Token 预算为主、字符预算为安全兜底。
- 摘要按“已确认事实、决定、待办、用户偏好、当前上下文、来源”组织。
- 保存摘要覆盖的消息序号、版本和上下文快照版本。
- 动态裁剪工具 Schema，普通问题不发送不需要的工具定义。
- 区分应用自己的摘要和 Provider Prompt Cache；分别统计缓存命中和上下文压缩。

### P1.2 工具注册与策略中心

当前进度：已完成工具目录第一阶段契约化。现有业务回调通过统一描述提供版本、能力、
风险、owner 作用域、权限语义、输入 Schema、超时/重试/幂等元数据和结果边界；Provider
Registry 使用同一筛选入口构建请求级 Tool Catalog，并在回调前校验 JSON 对象、必填字段、
声明字段、基础类型和枚举。原有工具名、owner 校验、业务参数校验和动作确认链路保持不变。
Skill 和现有业务工具现在都经过统一观测包装；只读工具执行超时和有限瞬时失败重试已经生效，写入草稿不自动重试。面试搜索、上下文列表、绑定/清除、日程和文件工具已经纳入第一批结果边界校验；外部 MCP 工具、简历/记忆/训练任务等领域的逐工具输出 Schema/结果验证和更细的权限策略仍待后续接入。

每个工具统一声明：

- 稳定名称、版本、输入 Schema 和输出 Schema；
- 只读/草稿/写入风险等级；
- 所需权限、是否需要人工确认；
- 超时、重试、幂等策略和结果验证器；
- 允许的会话范围和资源类型。

现有工具先适配到注册中心，再逐步增加工具，不改变已有 API 和动作状态机。

### P1.3 RAG 和 Skill 增强

- RAG 增加混合召回、重排、来源级权限和回答级引用。
- 增加检索命中、引用正确性、无答案拒答和答案 grounding 评测。
- Skill 增加版本、启用状态、适用范围和变更审计。
- 普通问题只有在模型判断确实需要时才加载 Skill 或 RAG。

### P1.4 可观测性和测试

- 当前进度：已增加按 `agentSessionId/runId` 串联的低敏 Agent Trace，覆盖路由、上下文构建、
  规划、模型开始/完成/重试、审批续跑、运行租约心跳和应用重启恢复，并提供 owner 隔离的 Trace 查询接口；
  活动页面展示短 Run 标识，避免同一会话中的多次运行只能看到模糊动作名称。仍需补齐
  Redis、数据库、外部检索等基础设施 span，以及真实 Provider 的完整模型轮次 usage 聚合；回答完成时还会记录来源元数据完整性状态，识别旧元数据、重复引用、版本冲突和权限来源冲突，但这仍不是事实级语义验证。
  ToolCallingAdvisor 会在内部递归并只向外层暴露聚合流，当前已记录每个外层模型流的首个
  非空输出 Trace，以及带 `modelTurnId` 的模型轮次开始/首 Token/完成事件、带 Run 内 `toolCallId` 的工具开始和逻辑调用完成/失败事件；回答完成时还记录低敏 grounding 和来源完整性状态，但仍不能证明 ToolCallingAdvisor 内部每个 provider tool-call 轮次和批次都被准确计量；因此仍需在 Provider/Advisor
  可观测边界增加真实契约测试。业务工具、Loop 观察工具和兼容日程路径现在都记录统一的开始/完成/失败事件；多轮交互评测还校验补充/确认/取消是否复用原 Run、是否重复插入用户消息。完整内部轮次、工具批次和更广的固定 Agent 评测集仍待后续实现。

- 为一次 Agent Run 建立统一 Trace ID，串联分类、规划、模型、工具、数据库、Redis 和恢复任务。
- 记录首 Token 延迟、队列时间、各阶段耗时、工具成功率、恢复次数、Token 和费用。
- 增加真实 Provider 契约测试、多轮 Tool Calling、审批恢复、崩溃恢复、并发会话和失败注入测试。
- 增加固定 Agent 评测集，并将工具正确性、安全拒绝、上下文引用和回答质量纳入回归门槛。

## 5. P2：外部连接和可选扩展

### P2.1 MCP Gateway

当前仓库只有 MCP 相关 Skill 资料，没有实际 MCP Runtime。后续接入时必须经过本地 Gateway：

- Server 白名单和工具白名单；
- OAuth、Scope 和最小权限；
- owner 映射、超时、限流、输出大小和审计；
- 外部结果统一视为不可信资料；
- 外部写操作继续使用本地草稿、确认、幂等和回滚策略。

### P2.2 外部会议和日历

先支持读取和草稿，之后再接入 OAuth/API：

- 日历查询；
- 飞书、腾讯会议、Zoom 等会议创建；
- 邮件或日历邀请草稿；
- 发送操作必须单独确认，不能因为“安排面试”直接发送外部消息。

### P2.3 有界子 Agent

只有当单 Agent 的上下文或任务复杂度确实达到瓶颈时，才增加简历分析器、RAG 研究器等有界子 Agent。子 Agent 必须拥有独立预算、权限、上下文和结果 Schema，不做自由协作式多 Agent 网络。

## 6. 不影响现有功能的约束

- 不修改原始面试报告、评分、回答和上传简历；所有变更继续使用独立草稿或新文件。
- 不改变旧面试详情进入 Agent 的兼容接口。
- 不让 Skill、RAG、文件或工具结果获得系统指令权限。
- 不让模型直接写业务表；写入必须经过服务端 owner、参数、状态、幂等和确认校验。
- 新功能默认关闭或只对新通用会话生效，旧会话保留原行为。
- 每个功能使用独立 `feature/*` 分支，先通过专项测试，再跑 Agent 相关回归和前端构建，最后合入 `develop-agent`。
- 未通过真实环境验收前不发布正式环境，不修改 `master`。

## 7. 每项功能的完成标准

1. 有明确的接口、状态和兼容边界。
2. 有正常、失败、重试、刷新、重启、并发和权限测试。
3. 旧面试、简历、RAG、Skill 和日程主流程回归通过。
4. 前端默认路径保持输入简单、结果清晰，内部 Loop 详情只作为高级诊断信息。
5. 能说明 Token、耗时、失败原因、恢复状态和是否产生业务副作用。

## 8. 与主流 Agent Runtime 的差距审计

### 8.1 当前已经达到的设计基线

- 仍采用受控单 Agent，而不是自由协作的多 Agent 网络；这更适合当前的面试、简历、知识库和日程场景。
- 意图路由、上下文选择和工具目录已经可以组合使用；普通问题不默认挂载业务工具，明确需要时才加载。
- ToolCallingAdvisor 已负责模型决策、工具执行、工具结果回传和继续生成；服务端额外保留有限 Loop、模型调用/总 Token/可选费用预算、工具调用预算和重试边界。
- 业务写入继续经过草稿、确认、owner 校验、幂等和审计；文件、报告、Skill 和 RAG 结果都按不可信资料处理。
- 会话消息、Loop 检查点、滚动摘要、基础恢复、来源摘要和 Token/费用记录已经存在。

### 8.2 必须补齐的生产能力

1. **真正的同一 Run 暂停/恢复**：审批确认已经可以把结果回传给原模型继续下一轮，并支持事务提交后崩溃恢复；下一步仍需保存可恢复的模型轮次、工具调用、结构化工具结果、审批项和 pending batch，不能只依赖动作表与摘要哈希。
2. **统一 Trace**：已完成第一阶段的 Agent Run 级 Trace，可串联路由、规划、上下文、模型开始/完成/重试、审批续跑和重启恢复；仍需补齐 Redis、数据库、外部检索等基础设施 span，并让 ToolCallingAdvisor 的内部模型轮次进入同一 Trace。
3. **工具契约完整化**：注册中心已补齐名称、版本、能力、风险、owner 作用域、权限语义、输入 Schema、幂等/重试元数据和回调前的基础输入校验；只读工具已接入契约级硬超时和有限瞬时失败重试，写入草稿工具默认不自动重试；仍需逐工具输出 Schema、结果验证器和更细的权限策略，不能只靠工具名称筛选。
4. **上下文预算和证据链**：已增加模型调用前的可配置输入预算和已有 RAG 来源校验；仍需精确 tokenizer、来源优先级/冲突处理、Skill 版本引用和统一“未找到依据”状态，避免模型有资料但回答无法解释来源。
5. **评测和真实契约测试**：需要固定问题集覆盖普通问答、面试报告引用、Skill+RAG 组合、日程创建/取消/修改、文件审核、注入攻击、审批恢复、重启恢复、并发会话和 Provider 失败切换。

### 8.3 可以后置的能力

- **MCP Runtime/Gateway**：当前仓库没有真正的 MCP Client/Server 运行时，不应直接把外部 MCP 工具挂进模型。后续必须先增加白名单、OAuth/Scope、owner 映射、限流、超时、结果净化和外部写操作确认。
- **多 Agent / 子 Agent**：当前单 Agent 还没有达到必须拆分的复杂度。未来如果简历分析、RAG 研究和面试训练出现独立预算、权限和输出协议，再引入有界子 Agent。
- **自动化外部操作**：日历、会议、邮件等外部系统先做读取和草稿；真正发送、取消或修改必须保留独立确认边界。

### 8.4 参考的主流运行时原则

- 可恢复 RunState 应包含足以继续执行的上下文、用量、模型响应、生成项和审批状态，而不是只保存展示轨迹或哈希摘要。
- Trace 应能区分模型轮次、工具调用、Guardrail 和自定义事件；否则出现“回答不对”时无法定位是路由、检索、工具还是模型造成的。
- 高风险工具应在工具边界做校验并暂停等待人工确认，确认后继续原运行，而不是另起一个孤立动作。
- 外部 MCP 的认证和授权必须是运行时边界的一部分，不能把发现到的工具列表直接视为可信权限。
